# 0018 — PGlite in development and tests, PostgreSQL in production

- **Date**: 2026-10-18
- **Status**: Accepted
- **Supersedes**: in part [0003](0003-postgresql-drizzle.md) (Docker in development)

## Context

With accounts (US-022), then collections (US-023), the API needs a **persistent** database. ADR 0003 chose PostgreSQL
and Drizzle, with a local database under Docker. But Docker is not installed on the project owner's workstation
(noted on 2026-10-18), it would also be needed in CI for the tests, and it slows down every start-up.

## Decision

- **PostgreSQL and Drizzle remain** the production choice (ADR 0003, Azure hosting, ADR 0008).
- In **development** and **tests**, the API uses **PGlite** (`@electric-sql/pglite`): the real PostgreSQL engine
  compiled to WebAssembly, embedded in the Node process. Same SQL, same migrations, same Drizzle schema.
- Chosen by configuration:
  - `DATABASE_URL` set (`postgres://…`) → PostgreSQL;
  - otherwise `BASE_LOCALE`: a folder (`.donnees/pglite` by default, ignored by Git) or `memory://` for an in-memory
    database, used by the tests and the e2e journeys.
- The SQL **migrations** generated by `drizzle-kit` (folder `apps/api/drizzle`) are applied **when the API starts**,
  whatever the database.

## Alternatives considered

- **Docker and PostgreSQL** (ADR 0003): faithful to production, but requires Docker everywhere; rejected for
  development and tests, kept as an option through `DATABASE_URL`.
- **SQLite**: lightweight, but a different SQL dialect from production, hence behaviour differences and two sets of
  migrations.
- **Home-made in-memory database**: no persistence, and nothing in common with production.

## Consequences

- `npm run dev`, the tests and the CI work **without Docker**; each API test creates its own in-memory database.
- PGlite serves only one connection at a time: enough for development, never for production.
- The `db:up` scripts and `docker-compose.yml` remain for anyone who wants to test against a real PostgreSQL.
